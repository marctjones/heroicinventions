Design document · draft 3

Heroic Inventions

A workshop game where players build historical machines one part at a time from real materials, then fire the boiler, open the valve or release the counterweight to see whether the machine works. Machines are written in Racket and run in Godot.

Updated 27 Sep 2026Design and control: Racket 9Runtime: Godot 4.6 .NET · C#Status: milestone 1 done, Racket machines run in Godotgithub.com/marctjones/heroicinventions

IVision

Players work at two levels. In Build mode they choose parts from a palette (axles, gears, pipes, valves, tanks, ropes, pulleys) and pick a material for each, such as oak, cedar, limestone or bronze. Parts snap together at typed ports. In Run mode the assembly becomes a physical system: gravity pulls, water flows, steam builds pressure, and parts can jam or break when a material is overstressed.

Behind the game is a machine language. Every machine, whether a built-in blueprint, a player's design or a mod, is a Racket program written in #lang heroic. Designers and advanced players can write machines as code, change them while they run, and test them like software. Casual players never see the code: the in-game editor reads and writes the same format.

The historical designs are the levels. Hero's Pneumatica and Vitruvius's De Architectura Book X describe machines in enough detail to rebuild, and both are public domain.

Closest existing game: Besiege, a Unity-based siege-machine builder. It has no fluids, heat, material strength, historical designs or programmable machine language. Those are what set this game apart.

IIArchitecture

The design follows the pattern that has worked best in industry: a Lisp controlling a native engine. Racket does what Lisps do well: describing, generating, checking and changing structure. Godot and C# do what needs predictable speed: rendering, rigid-body physics and the per-tick simulation solvers.

Racket

design, generation, checking, live control

  • #lang heroic: the language machines are written in
  • Compile-time checks with exact source locations
  • Part shapes generated from formulas (gears, screws, pulleys) and exported to glTF
  • Materials and part catalogues as source data
  • REPL connected to the running game
  • Machine tests with rackunit

Godot + C#

runtime: every frame, every physics tick

  • Rendering, camera, UI, the in-game editor
  • Jolt rigid bodies and joints
  • Fluid, thermal and electrical network solvers (HeroicInventions.Sim)
  • Reader for the .machine format (loads machines without Racket)
  • Live-link server that accepts commands from the REPL
  • Headless simulation host for automated tests

The boundary between the two is a data format, not a shared runtime. Racket never runs inside the Godot process, so there is no clash between two garbage collectors, no need to ship Racket with the game, and no foreign-function interface to maintain. The shipped game needs only Godot. Racket is present during design, testing and live sessions.

IIIRacket layer

A language for machines built · M1

A machine file is a full Racket module. Parts and links are declared with clause forms, and every parameter value is an ordinary Racket expression, so a design can use variables, helper functions and unit conversions.

racket/machines/aeolipile.rkt
#lang heroic
;; Hero of Alexandria's aeolipile: a bronze sphere on an axle over a
;; boiler, spun by the reaction of two bent steam nozzles.

(define sphere-radius (cm 6))

(define-machine aeolipile
  #:source "Hero of Alexandria, Pneumatica"
  (boiler kettle #:at (0 (cm 8) 0) #:radius (cm 12) #:height (cm 16)
          #:water (kg 0.3) #:fire (W 3000) #:material bronze)
  (rotor ball #:at (0 (cm 45) 0) #:radius sphere-radius #:wall (mm 1)
         #:material bronze #:nozzles 2 #:bore (mm 2)
         ;; Nozzle tips sit 2 cm beyond the sphere's surface.
         #:arm (+ sphere-radius (cm 2)))
  (connect kettle.steam ball.steam-in))

Helper functions position parts. This file drops four cubes in a row at staggered heights:

racket/machines/material-samples.rkt
(define size (cm 15))
(define (slot i) (+ -0.35 (* i 0.25)))  ; x position of the i-th cube
(define (drop i) (+ 1.2 (* i 0.2)))     ; staggered drop heights

(define-machine material-samples
  (block cedar-cube   #:at ((slot 0) (drop 0) 0.3) #:size size #:material cedar)
  (block oak-cube     #:at ((slot 1) (drop 1) 0.3) #:size size #:material oak)
  (block granite-cube #:at ((slot 2) (drop 2) 0.3) #:size size #:material granite)
  (block bronze-cube  #:at ((slot 3) (drop 3) 0.3) #:size size #:material bronze))

In milestone 1, each part is written as its own clause, so its name and ports are known while the file compiles. Generating parts in loops, such as a pulley block with any number of sheaves, comes with the crane milestone. Those parts will be checked when the module runs, still with source locations.

Checking at compile time built · M1

define-machine is a macro built with syntax-parse, so its rules run while the file compiles, before anything is simulated. It checks:

  • part names are unique;
  • every material is in the material table;
  • every part.port reference exists;
  • pipes join water ports and steam connections join a boiler to a rotor;
  • every rotor has steam;
  • sealed-air groups contain only tanks.

Required and duplicated options are reported too. This is the real output of racket on a machine that connects a boiler to a water tank:

broken.rkt:6:24: define-machine: cannot join kettle.steam (steam port) to vat.drain (water port)
  at: vat.drain
  in: (define-machine broken-aeolipile ...)

A reference to a port that doesn't exist lists the ports that do: kettle is a boiler with no port named spout; its ports are: steam. DrRacket highlights the offending reference.

The .machine format built · M1

racket racket/build.rkt runs each machine module and writes a .machine file to game/machines/. The file holds plain S-expressions with every expression already evaluated and every number a finite decimal. The C# side reads it with a small parser and needs no Racket. Each clause keeps its source location. The generated files are committed, like compiled assets, so the game runs from a fresh clone.

game/machines/aeolipile.machine
;; Generated by #lang heroic from racket/machines/aeolipile.rkt. Do not edit: change the Racket source and rebuild.
(machine aeolipile
  (source "Hero of Alexandria, Pneumatica")
  (part kettle boiler (material bronze) (at 0.0 0.08 0.0) (props (radius 0.12) (height 0.16) (water 0.3) (fire 3000.0)) (ports (steam steam 0.16)) (srcloc "racket/machines/aeolipile.rkt" 9 2))
  (part ball rotor (material bronze) (at 0.0 0.45 0.0) (props (radius 0.06) (wall 0.001) (bore 0.002) (arm 0.08) (nozzles 2.0)) (ports (steam-in steam 0.0)) (srcloc "racket/machines/aeolipile.rkt" 11 2))
  (connect (kettle steam) (ball steam-in) (srcloc "racket/machines/aeolipile.rkt" 15 2)))

The C# runtime checks every reference again, because the in-game editor and hand edits will also produce these files. Its errors quote the Racket location, for example racket/machines/broken.rkt:4:2: nowhere is not a tank in this machine. Racket reads the same files back with its built-in read, so a machine saved by the editor can be opened in DrRacket and turned into code.

Geometry generated from formulas built · M4

Many ancient machine parts have a shape that follows from a few numbers. heroic/geometry generates them, and racket/build.rkt writes each as a binary glTF file (game/meshes/<stem>.glb) that the game loads at runtime:

  • Gears: tooth profile from tooth count and module. Involute teeth (constant ratio; worked out in the 1700s) or triangular teeth, which is what the Antikythera mechanism's gears actually have. mate-angle phases a gear so its teeth fall between its partner's; the tests check involute pairs stay in mesh through two teeth of rolling.
  • Archimedes' screws: helix from pitch, starts, turns and radius; vitruvian-screw derives all of them from the length alone (X.6).
  • Pulleys, drums, treadwheels and norias: radius, groove, spokes, treads, buckets and paddles.
  • Torsion catapults: every dimension of the two-armed catapulta scaled from the bolt length by Vitruvius's table (X.10). Each entry records whether the number is as the text reads, emended, or reconstructed.

Every mesh is a closed solid, and its volume and moments of inertia are computed exactly from it, so the game's mass and rotational inertia are the material's density times the real shape. Parts use them through the wheel, screw and fixture clauses. The build also writes a catalogue of standard sizes (game/meshes/catalogue/) for the in-game editor to offer.

Live link planned · M2

A Racket REPL will connect to the running game over a local TCP socket. Messages in both directions are S-expressions, one per line.

;; REPL → game
(load-machine "game/machines/aeolipile.machine")
(run)
(set! (kettle fire) 5000)
(subscribe (ball rpm) (kettle pressure) #:hz 10)
(redefine-part ball (rotor #:radius (cm 7) …))   ; keeps the running state

;; game → REPL
(telemetry 41.2 (ball rpm 312.0) (kettle pressure 18400.0))
(event 55.8 break post-l "tension 91 MPa exceeds bronze" (srcloc "racket/machines/aeolipile.rkt" 7 2))

redefine-part swaps in a new part but keeps the simulation state of every part whose name is unchanged. A break event carries a source location, so the REPL can jump to the part that failed. Until the live link exists, rebuild with racket racket/build.rkt and press R in the game to reload.

Machines as tests built · M3

Behaviour claims will be written as rackunit tests that run the real C# simulation through a headless host:

(test-case "Heron's fountain lifts water above its basin"
  (define run (simulate herons-fountain #:seconds 60))
  (check-true (> (max-of run '(nozzle jet-height)) 0.0)))

simulate (heroic/simhost) runs the machine in HeroicInventions.SimHost, a console host for the C# solvers with no Godot, and returns sampled telemetry.

Rigid bodies, joints, ropes and contacts live in Jolt, inside the game, so they get a second runner. godot-simulate (heroic/godothost, M10 #26) runs the real game headless with --fixed-fps, stepping exactly as in play but as fast as the machine allows, and returns frames of the same shape. Each frame adds every body's centre of mass, velocity, rotation, hinge angle, spin and contacts, every rope's tension, and the scene's kinetic and potential energy, so final-of, max-of and min-of work on both:

(test-case "a pendulum keeps Huygens' time"
  (define run (godot-simulate 'fall-and-swing #:seconds 10 #:sample-dt 1/120))
  ...)

Its first run found two things the eye had missed: Jolt's gravity was Godot's default 9.8 m/s² against the sim core's 9.81 (now one value, set from the sim), and every body carries Godot's default damping of 0.1 per second, a stand-in for air drag that the tests now state openly until air drag (#33) replaces it.

IVGodot layer

Godot handles everything that runs every frame and must keep a steady frame rate. It works entirely from .machine data and generated meshes, so it has no dependency on Racket.

  • Machine reader (built): a short S-expression parser in C# that produces a MachineDef.
  • Instantiation (built for tanks, pipes, sealed air, boilers, rotors, blocks, levers, pendulums, ramps and generated wheels, screws and fixtures): MachineRuntime builds the solvers, and MachineView builds the scene for any machine without machine-specific code. Joints (hinge, gear, rope) come with the crane milestone.
  • Solvers: HeroicInventions.Sim, the engine-independent C# library from the scaffold, stepped on every physics tick at 120 Hz.
  • Editor (planned): drag-and-drop building with port snapping. It saves .machine files.
  • Live-link server (planned): active only in development builds. It turns incoming S-expression messages into actions on the scene and sends telemetry back.
  • Headless host (built): the same solvers run without rendering, for Racket's tests and for continuous integration.

Measured in the game's own physics (Jolt at 120 Hz, game/scenes/CartEval.tscn, checked by heroic/tests/cart-eval-test.rkt): a 28 kg cart, four 2 kg disc wheels of 15 cm radius on hinges, on a 10° slope and coasting at 2 m/s.

They match the formulas to about 2% with nothing added but a rolling-resistance torque; VehicleBody3D under Jolt does not roll freely (its drivetrain brakes with no engine force and no brake set), so it cannot model an honest cart. Two things to carry into #25: the coasting figure is Crr g only for light wheels, and with these wheels it is 12.5% lower because the wheels store kinetic energy; and Godot's default damping of 0.1 per second costs a fifth of the slope acceleration by 3 m/s, so #33's zero damping matters before any rolling-resistance number can be trusted. Jolt has no rolling resistance of its own: add a torque Crr N r against each wheel's spin.

VSimulation

No game engine simulates rigid bodies, water and steam well together. Jolt handles parts that move. The C# library handles the working fluids with lumped network models, the approach engineering tools such as Modelica and Simscape use. Couplings pass forces and flows between the two on every tick.

Fluid network

Each tank has an elevation, a cross-section area and a water volume. The head at a pipe port is the tank's gas pressure converted to metres of water, plus the water surface height, or the port's own height if the port sits above the water. Flow is proportional to the head difference between the pipe's ends. A sealed AirPocket joins tanks and follows Boyle's law (P·V = constant). That is all Heron's fountain needs: its jet height and the moment it stops both come out of the model rather than being scripted.

Thermal network

The boiler holds water and steam in equilibrium, so its pressure is the saturation pressure at its temperature (Antoine equation). Heat from the fire raises the temperature. Steam leaving the boiler removes latent heat, 2.257 MJ/kg, and that balance sets an aeolipile's top speed for a given fire.

Couplings built · M6

  • Jet thrust = steam mass flow × exit velocity, capped at the speed of sound in steam (about 470 m/s).
  • Ropes and chains (rope): one-sided length constraints between two parts or a part and a fixed point, optionally over pulleys, winding onto a drum, released as a sling, or nocked like a bowstring. Jolt has no rope joint, so all ropes are solved together each tick by sequential impulses, sized by each end's effective mass (its inertia about its hinge for a hinged part). A rope breaks when its tension exceeds its material's tensile strength × cross-section.
  • Arbors and gears (arbor, mesh): wheels keyed to one shaft turn as one; a gear driven by a crank drives every gear meshed with it at −(teeth ratio), phase-locked so teeth stay interleaved. The game checks meshing gears share a module and sit their pitch radii apart. A cranked train's driven gears don't load the crank (right for clockwork, not a power train).
  • Driven, loaded gear trains (#113; (mesh a b #:efficiency η), a waterwheel, windmill or jetwheel on an arbor): a train with no crank is turned by whatever turns its gears and its load slows that driver. One coupling point joins the sim's turning parts and Jolt's bodies: the momentum exchange of the world's shafts (#78, ShaftLink between two IShaft ends). Each mesh is a link of ratio −(teeth driving / teeth driven) with its efficiency (power passing forward costs the driver 1/η); a sim-turned part on an arbor is a link of ratio ±1 to the arbor's first Jolt wheel. Each tick, after the sim steps its parts (water in the buckets, wind on the sails) and before Jolt steps its bodies (a brake, a rod pushing a saw), the links trade the least angular momentum that puts every pair back on its ratio, a few Gauss–Seidel sweeps for a train; a load slows its gear during Jolt's step and the next exchange takes ratio × torque / η from the driver. A gentle angle pull keeps teeth in their gaps. A bearing in a driven train rubs after the exchange, at the train's speed, clamped against the inertia of everything geared to it, so a brake stops the whole train and its heat is the train's energy. Checked by geared-brake (1 kg·m² at 36 rpm into a 0.1 N·m brake through 10:1: stops in 3.77 s, 3.40 s at η 0.9; at 60 rpm the brake shaft would pass the 47.1 rad/s Jolt lets a body spin, so the issue's 60 rpm case, 6.28 s and 5.65 s, is checked on the sim side) and hierapolis-sawmill. Not yet: a rolling cart wheel as the driver (its axle rides on the chassis, not a fixed hinge), or a cranked train that loads its crank.
  • Torque-limited drives (#:drive-torque): men in a treadwheel or at a screw can only push so hard; a load too heavy for them wins.
  • Water lifting (lift): a screw's pockets are computed from its tilted helical channel (each dip fills to the lowest crest on its downhill side); a noria's buckets from their shape; a pump's piston by bore × stroke. The torque of lifting (ρ·g·H·V/2π) acts back on the machine. A noria's river pushes its submerged paddles with ½·ρ·Cd·A·(v − u)².
  • Atmospheric cylinder (atmospheric-cylinder, Newcomen): steam flows in from the boiler; cold injection condenses it toward the vapour pressure of water at the injection temperature; the piston feels (atmosphere − cylinder pressure) × area. The heat lost re-warming the cylinder walls isn't modelled, so it's ~5× more efficient than real Newcomen engines.
  • Flowing water, level 1 (inflow, channel, lift #:current-from): an inflow is water arriving from beyond the scene (a spring, a river from upstream) at a set rate — the world outside isn't modelled, only what it brings. A channel is an open stone trough from a tank's port to another tank's port, or #:to off out of the scene. How much it carries is a broad-crested weir over the port's lip, Q = 1.705·b·h1.5 (h reduced if the far end is backed up); how deep and fast it runs is Manning's normal depth for its slope and n = 0.015. A noria given #:current-from a channel is pushed by that channel's velocity, so the river really drives it: the Hama noria's race runs 500 L/s, 27.5 cm deep at 1.52 m/s, and turns the wheel at 1.3 rpm; choke the river to 300 L/s and it drops to 0.5 rpm, at 200 L/s it stalls. In the game each channel shows its water at the computed depth with foam riding at the computed speed, and a falling sheet where it spills into a lower pool. Not modelled (level 2): water spreading over terrain, or flow that varies along a channel.
  • Torsion springs (#:spring-stiffness on a lever): torque −k·(θ − rest), counted in the energy dashboard.
  • Not yet: stress-based breaking of solid parts (only ropes break), and a world-level river or wind that parts can stand in (a noria's current is its own parameter).

Electricity is almost free. A lumped electrical circuit uses the same equations as the fluid network: voltage takes the place of head, current the place of flow, and a capacitor behaves like a tank. The Franklin domain can reuse the fluid solver with different units.

IXDecisions

Why Racket for the control layer

Lisp advantageWhere it shows up in this game
Code is dataMachines, save files and live-link messages all use one S-expression format. Racket reads it with read, and a player's saved design can be opened as code.
Macrosdefine-machine checks ports, materials and connections at compile time, with the exact source location of any error.
A full language inside the DSLPulley blocks, gear trains and catapults scaled from Vitruvius's tables are written as functions and loops, not copied by hand.
Changing a running programThe REPL redefines parts in the running game while keeping their simulation state.
Language toolingWith #lang, DrRacket provides syntax colouring, name arrows, error highlighting and a debugger for machine files.
Trees are nativeMachines are trees of assemblies, and generated geometry is built from nested transforms. Both are natural list structures.

Where Racket stays out

  • The per-tick loop. Solvers and Jolt run in C# and C++ so that Racket's garbage collector can never cause a frame stutter.
  • The shipped game. Players need only Godot. Racket is a design-time and development-time tool.
  • The Godot process. Racket is never embedded in Godot, so there is no foreign-function bridge to maintain, and a Racket error cannot crash the game.

This follows well-proven practice. Naughty Dog used Racket (then PLT Scheme) to compile game data for its PS3 games while a C++ engine ran them, as Dan Liebgold described at RacketCon 2013. AutoLISP has scripted AutoCAD's 3D engine since the 1980s.

Why Godot

Godot 4.6 (.NET)

Pros

  • MIT licence. No fees, royalties or revenue thresholds, ever.
  • Open source. Physics or rendering can be patched when needed.
  • Jolt ships built in and is fast and stable for jointed mechanisms.
  • Small, fast editor. Opening the project and pressing Play takes seconds.
  • The node tree maps naturally onto the machine tree that Racket produces.

Cons

  • C# projects cannot export to the web yet. It is being worked on but has no release date.
  • Smaller asset ecosystem, with no off-the-shelf fluid or rope packages.
  • Most tutorials use GDScript, so C# examples are rarer.
  • Requires the separate .NET edition of the editor.

Unity 6 (not chosen)

Pros

  • C# builds export to WebGL.
  • PhysX ArticulationBody gives exact jointed chains for gear trains and linkages.
  • Asset Store add-ons such as Obi Rope and Obi Fluid.
  • Very large C# tutorial base.

Cons

  • Closed source. The engine cannot be changed below the scripting layer.
  • Licensing history, including the 2023 runtime-fee reversal and revenue thresholds.
  • Heavier editor, with slower script reloads.
  • Its scripting runtime trails current .NET.

The engine choice stays reversible. Machines live in Racket and .machine files, and the solvers live in an engine-independent C# library. Only the view layer depends on Godot. For a browser demo before Godot supports C# on the web, the same solver library can run in a browser through Blazor (.NET compiled to WebAssembly) and read the same .machine files.

The Godot project sits in its own game/ folder because the Godot C# build compiles every .cs file under its project folder and the editor imports every file there. Racket sources stay outside it for the same reason. Only their generated output goes in.

From here the work is organised in five stages, each ending in something playable, so the game builds out from a working sandbox: 1 Sandbox world (point-and-click building of any machine, many machines running together in one world, editing while it runs, saving), 2 Mechanisms (Heron's toolkit on Earth), 3 Ground and water, 4 Heat and air, and 5 The Lonely Rover, the Mars game built on all of it, with 6 Later for exploratory work. The stages and their issues are listed in The Lonely Rover's build order and on the GitHub milestones.
